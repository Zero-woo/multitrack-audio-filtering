# 문서 작성 규칙

프로젝트 문서는 대화 이력을 모르는 외부 독자가 목적, 사용법, 검증 범위와 한계를 이해할 수 있도록 작성한다.
README와 `docs/`의 기술 문서, 유지보수 기록에 같은 평서형 문체를 적용한다.

## 문체와 시제

- 기능·계약·정책은 현재형 `~한다`, `~이다`, `~로 구성된다`로 기술한다.
- 수행한 실험과 관측 결과는 `~하였다`, `~로 나타났다`, `~을 확인하였다`로 기술한다.
- `~합니다`, `~했습니다`, `~하세요`와 같은 경어체나 독자에게 직접 요청하는 문장을 사용하지 않는다.
- `이번 작업`, `다음 세션`, `사용자가 요청하여`, 토큰 소진·재개 등 대화 진행 상황은 공개 문서에서 제외한다.
- 조사 당시의 사실에는 기준일·대상 revision·설정을 명시한다. 과거의 미구현 상태를 현재 상태로 표현하지 않는다.

| 수정 전 | 수정 후 |
| --- | --- |
| Batch 처리를 완료했습니다. | `batch-infer`는 여러 stem을 순차 추론하고 유효한 cache를 재사용한다. |
| 테스트가 모두 통과했습니다. | 해당 설정의 실행 결과는 97 passed로 나타났다. |
| 자세한 내용은 문서를 확인하세요. | 입력 형식과 예외 처리는 Phase 3 문서에 정의한다. |
| 다음 단계에서 판정을 구현할 예정입니다. | 판정 정책은 Phase 7 모듈이 담당한다. |

## 구성과 검증 정보

개요와 적용 범위를 먼저 설명하고 입력·출력, 처리 과정, 설정·사용 예, 검증 결과, 한계 순으로 구성한다.
실행 명령이나 필드 정의가 많은 문서는 표와 소제목으로 탐색을 돕는다. 모든 문서에 동일한 목차를
기계적으로 강제하지 않으며 기존 링크와 재현에 필요한 명령·schema·단위·hash는 보존한다.

검증 기록은 실행 환경, 대상 자료, 적용 설정, 결과와 해석 범위를 함께 기술한다.
구현 여부와 실제 데이터에서의 성능을 구분하고, synthetic reference나 예제 threshold를
실제 정답 또는 보정된 운영 기준으로 표현하지 않는다. 문체 수정만으로 새로운 검증을 수행한 것으로 기록하지 않는다.

## 코드와 유지보수 기록

코드 식별자, CLI 인자, JSON key와 오류 코드는 원문을 유지한다. 설명문과 코드 예제의 주석은
평서형으로 작성한다. 외부 원문·라이선스·attribution은 문체 통일을 위해 변형하지 않는다.

공개 README는 프로젝트의 목적과 실행 경로를 안내하고, 세부 계약은 해당 Phase 문서에 둔다.
로컬 산출물 위치·Git 이력·환경 정보는 `HANDOFF.md`에 기록한다. 문서만 변경한 경우에는
링크·명령 형식·수치 보존과 diff를 확인하며, 실행 코드를 변경하지 않았다면 모델 추론을 반복하지 않는다.
